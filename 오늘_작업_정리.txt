최종 구조:
- SocialMediaPost (1개 모델)
  - 공통 필드 (title, content, author, likes_count 등)
  - Reddit 전용 필드 (subreddit, upvotes, downvotes, score, thumbnail_url)
  - DC Inside 전용 필드 (gall_name, post_num, ip, images)

- BaseSocialMediaPostSerializer (기본 Serializer)
  - RedditPostSerializer (Reddit 전용)
  - DCInsidePostSerializer (DC Inside 전용)

선택 이유:
- 플랫폼이 2개뿐이라 단일 테이블이 효율적
- JOIN 없이 쿼리 가능
- 플랫폼별 필드에 인덱스 직접 적용 가능
- Serializer는 플랫폼별로 분리해 필드 노출 제어

- 현재 구조의 장점

DB 관점:
- 쿼리 성능 우수: JOIN 없이 단일 테이블에서 모든 플랫폼 데이터 조회 가능
- 인덱스 활용 용이: 플랫폼별 필드(subreddit, gall_name)에 직접 인덱스 적용 가능
- 단순한 쿼리: 모든 플랫폼 게시물 조회 시 UNION이나 복잡한 JOIN 불필요
- 저장 공간 효율: NULL 필드는 거의 공간을 차지하지 않음

개발 관점:
- 코드 단순성: 하나의 모델로 모든 플랫폼 데이터 관리
- ORM 활용: 플랫폼별 필드에 직접 접근 가능 (post.subreddit, post.gall_name)
- 유지보수 용이: 스키마가 명확하고 이해하기 쉬움
- Django Admin 지원: 하나의 테이블에서 모든 플랫폼 데이터 관리 가능

API 관점:
- Serializer 분리: 플랫폼별로 필요한 필드만 노출하여 API 응답 최적화
- 동적 Serializer 선택: ViewSet에서 플랫폼에 따라 적절한 Serializer 자동 선택
- 검증 로직 분리: 플랫폼별 특화된 검증 로직을 각 Serializer에 구현
- 확장성: 새 플랫폼 추가 시 BaseSocialMediaPostSerializer를 상속받아 쉽게 확장 가능

확장성 관점:
- 플랫폼 추가 용이: 새 플랫폼 필드를 모델에 추가하고 Serializer만 만들면 됨
- 마이그레이션 관리: Django 마이그레이션으로 스키마 변경 추적 가능
- 데이터 무결성: DB 레벨 제약 조건 적용 가능

- 주요 질문과 답변

Q1: Model과 Serializers 구조 및 DB 저장 방식 설명
- Model: DB 스키마 정의로 Single Table Inheritance (STI) 패턴 사용
  - 하나의 테이블(data_collector_socialmediapost)에 모든 플랫폼 데이터 저장
  - 공통 필드와 플랫폼별 특화 필드를 모두 포함
  - Reddit 게시물은 subreddit, upvotes 등 Reddit 필드만 사용하고 DC Inside 필드는 NULL
  - DC Inside 게시물은 gall_name, post_num 등 DC Inside 필드만 사용하고 Reddit 필드는 NULL
  - 플랫폼 구분은 source 외래키를 통해 SocialMediaSource의 platform 필드로 확인
- Serializer: API 응답 형식 정의로 플랫폼별로 분리
  - BaseSocialMediaPostSerializer는 공통 필드와 메서드 제공
  - RedditPostSerializer는 Reddit 전용 필드만 노출
  - DCInsidePostSerializer는 DC Inside 전용 필드만 노출
  - ViewSet에서 플랫폼에 따라 적절한 Serializer를 동적으로 선택

Q2: SocialMediaSourceSerializer vs BaseSocialMediaPostSerializer 차이
- SocialMediaSourceSerializer: 소스 정보 (어디서 수집할지)
- BaseSocialMediaPostSerializer: 게시물 정보 (수집한 내용)
- 서로 다른 모델을 직렬화하므로 합칠 수 없음

Q3: 1개 모델 vs 분리 모델 비교
- 1개 모델 (현재): 쿼리 성능 우수, JOIN 불필요, 인덱스 활용 용이
- 분리 모델: 확장성은 좋지만 UNION 필요, JOIN 오버헤드
- 결론: 현재 상황(플랫폼 2개)에서는 1개 모델이 적합

Q5: tasks.py 필요성
- services.py: 실제 수집 로직 (동기 실행 가능)
- tasks.py: Celery를 통한 비동기 실행, 재시도, 모니터링
